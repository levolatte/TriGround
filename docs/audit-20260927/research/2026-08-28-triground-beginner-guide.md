## 1. 先记住一句话

这个仓库做的事情就是：

> 给模型三张同一场景的图片，再问它“某个东西在哪里”，让它返回一个矩形框。

三张图片分别是：

- RGB：普通彩色照片；
- IR：红外图，适合看夜间、低照度或热目标；
- Depth：深度图，表示物体离相机多远。

再加一句 Query（查询），例如：

> “车辆旁边的行人。”

模型最后输出：

```json
{"bbox_2d":[120,210,380,840]}
```

这四个数字表示目标框左上角和右下角的位置。

## 2. 比赛任务到底是什么

假设图中同时有汽车和行人：

```text
┌──────────────────────────────┐
│                              │
│       汽车       行人         │
│      ┌────┐     ┌──┐         │
│      │    │     │  │         │
│      └────┘     └──┘         │
│                              │
└──────────────────────────────┘
```

Query 是：

> “汽车右边的行人。”

模型要输出行人的框：

```text
[x1, y1, x2, y2]
```

四个坐标的含义是：

- `x1`：框左边的位置；
- `y1`：框上边的位置；
- `x2`：框右边的位置；
- `y2`：框下边的位置。

仓库中的训练数据使用 0～1 的归一化坐标，例如：

```json
[0.12, 0.21, 0.38, 0.84]
```

意思不是第 0.12 个像素，而是：

- 左边在图像宽度的 12%；
- 上边在图像高度的 21%；
- 右边在图像宽度的 38%；
- 下边在图像高度的 84%。

送给 Qwen 学习时，代码再把它乘以 1000：

```json
{"bbox_2d":[120,210,380,840]}
```

让语言模型生成整数，通常比生成很多小数更稳定。对应实现位于 `src/mm_grounding/data.py` 的 `NativeGroundingCollator`。

## 3. 比赛怎么判断预测对不对

核心指标是 ACC@0.5。理解它之前，需要先理解 IoU（Intersection over Union，交并比）。

假设：

- 红框是真实框；
- 蓝框是模型预测框。

IoU 的计算是：

```text
两个框重叠的面积
────────────────
两个框合起来的总面积
```

如果两个框完全一样：

```text
IoU = 1
```

如果完全不相交：

```text
IoU = 0
```

如果 IoU 至少达到 0.5，这条 Query 就算预测正确。

例如一共 100 道题：

- 68 道题 IoU ≥ 0.5；
- 32 道题 IoU < 0.5。

那么：

```text
ACC@0.5 = 68 / 100 = 0.68
```

队友仓库当前 README 记录的比赛结果是：

| 路线 | 比赛 ACC@0.5 |
| --- | ---: |
| RDT 弱监督路线 | 0.6404 |
| 并行 adaptor 后融合 | **0.6785** |

也就是说，第二条路线每 100 道题大约比第一条多做对 3.81 道。

## 4. Qwen 在里面扮演什么角色

Qwen3-VL 是一个能同时处理图片和文字的大模型。可以粗略拆成两部分：

```text
图片
 ↓
视觉主干：把图片转换成许多视觉 token
 ↓
语言模型：结合 Query 理解这些 token
 ↓
生成文字答案
```

这里的 token 可以先理解为“模型能够处理的小块信息”。

图片会被切成许多 patch（图块）：

```text
原图
┌───────────────┐
│ ① │ ② │ ③ │ ④ │
├───┼───┼───┼───┤
│ ⑤ │ ⑥ │ ⑦ │ ⑧ │
└───────────────┘
```

每个小块经过视觉编码后变成一串数字。Qwen 再根据这些数字和 Query 生成答案。

队友没有让模型输出传统检测器常见的数值张量，而是让 Qwen 像回答问题一样输出文本：

```json
{"bbox_2d":[120,210,380,840]}
```

随后代码从这段文字中解析出坐标。所以它本质上是：

> 用语言模型“说出”边界框，而不是用传统检测头直接回归边界框。

仓库中没有 GroundingDINO、候选框生成或 reranking（重排序）链路。

## 5. 队友没有重新训练整个 Qwen

这是理解仓库最重要的一点。

Qwen3-VL-2B 有大约 20 亿参数。如果全部训练：

- 很耗显存；
- 很耗时间；
- 容易把 Qwen 原有能力训坏；
- 目标域数据少时容易过拟合。

所以队友把 Qwen 主干冻结了。

“冻结”可以理解为：

> Qwen 原来的参数不准修改，只允许新加的小模块学习。

新模块主要有两类：

- adaptor：适配器；
- fusion：融合器。

可以把 Qwen 想象成一个已经很聪明，但主要熟悉彩色照片的人。现在要给它红外和深度图，它不一定懂，因此给它配两个翻译员：

```text
IR 图 ── IR adaptor ──┐
                       ├── 告诉 Qwen 哪些信息有用
Depth ─ Depth adaptor ─┘
```

训练时主要训练这两个翻译员和负责协调它们的融合器，不改 Qwen 本身。

所有当前发布配置都关闭了：

- Vision LoRA；
- 辅助 bbox head；
- Qwen 主干训练。

所以发布的 `.pt` 文件只有几十 MB，而不是整个 Qwen 的数 GB。使用发布权重时仍需另行取得 Qwen3-VL-2B-Instruct 主干。

## 6. 为什么需要 RGB、IR、Depth 三种图

三种模态各有长处。

### 6.1 RGB

RGB 就是普通照片。

优点：

- 颜色和纹理丰富；
- Qwen 本来就比较熟悉；
- 白天表现通常最好。

缺点：

- 夜间或低照度下可能看不清；
- 黑色目标和背景可能混在一起。

### 6.2 IR

IR 是红外图。它通常不提供正常颜色，但夜间可能更容易看到人、车辆等目标。

优点：

- 夜间和低照度更有用；
- 某些热目标更突出。

缺点：

- 纹理比 RGB 少；
- 不一定所有目标都有明显热特征；
- 与 RGB 稍微错位就可能产生误导。

### 6.3 Depth

Depth 是深度图，告诉模型每个位置大概离相机多远。

优点：

- 有利于区分前后关系；
- 对“最近的”“后面的”“车旁边的”可能有帮助；
- 颜色相似但距离不同的目标可以分开。

缺点：

- 有大量无效值；
- 远距离目标可能不稳定；
- 深度单位不正确会破坏输入意义。

队友的核心目标不是“总是相信 IR 和 Depth”，而是：

> 当辅助模态可靠时使用它，不可靠时尽量退回 RGB。

## 7. 仓库有两条主要路线

整个仓库的模型实验可以归纳为两条主线：

1. RDT-deep 弱监督路线；
2. 并行三流、独立 adaptor 预训练后融合路线。

### 7.1 路线一：RDT-deep

README 把它叫作“弱监督早期融合”，但从代码看，它实际上比“早期融合一次”更复杂。

大致流程是：

```text
IR ───┐
      ├── 形成辅助视觉提示
Depth ─┘
          ↓
RGB → Qwen视觉块1 → 视觉块2 → 视觉块3 → …… → 最终视觉特征
          ↑           ↑           ↑
       注入提示     更新并注入    更新并注入
```

具体过程：

1. IR 和 Depth 先被转换成提示；
2. RGB 进入 Qwen 视觉主干；
3. 在每一个 Qwen 视觉块之前，辅助提示都会根据当前 RGB 特征更新；
4. 更新后的提示再注入 RGB；
5. 最后 Qwen 根据融合后的 RGB 特征生成 bbox。

可以把它想成：

> RGB 是正在解题的学生，IR 和 Depth 每走一步都在旁边小声提醒它。

代码主要位于：

- `src/mm_grounding/model.py` 的 `_rdt_deep_prompt_vision_forward`；
- `src/mm_grounding/adapters.py` 的 `RDTRecurrentPromptBlock` 和 `RDTDeepFusion`。

#### RDT 路线怎么训练

第一步使用约 7,200 条弱监督数据训练。

所谓弱监督，可以简单理解为：

> 数据数量多，但标注和文字描述不一定很干净。

例如通过已有 bbox 自动生成：

- “左边的人”；
- “第二辆车”；
- “路灯旁边的行人”。

这种方法便宜，但可能产生错误：

- 方位关系不准确；
- “第二个”排序不稳定；
- bbox 本身有噪声；
- 描述可能直接泄露 bbox 的几何位置。

训练过程是：

1. 前两轮使用学习率 `4e-5`；
2. 再用更低学习率续训到第 5 轮；
3. 最后使用 923 条人工复核目标域数据微调 1 轮；
4. 使用独立的 119 条验证数据选择模型。

对应配置：

- `configs/multimodal_rdt_deep_reviewed.yaml`；
- `configs/multimodal_rdt_deep_reviewed_extend_e5.yaml`；
- `configs/triground_rdt_ws_v1_manual_ft1.yaml`。

最终比赛正确率记录为：

```text
0.6404
```

### 7.2 路线二：并行 adaptor 后融合

这是比赛成绩更高的路线。

核心思想是：

> 不要一开始就让不懂红外和深度的融合器胡乱学习；先分别把 IR 和 Depth 分支教会，再让它们合作。

可以把它想象成：

- 先单独培养一个红外专家；
- 再单独培养一个深度专家；
- 最后让两个专家和 RGB 一起开会。

大致结构：

```text
RGB ─── Qwen视觉块1 ─ Qwen视觉块2 ─ …… ─┐
                                         │
IR  ─── 同一视觉块1 + IR适配器 ─ …… ─────┤
                                         ├─ 联合融合 → Qwen语言模型 → bbox JSON
Depth ─ 同一视觉块1 + Depth适配器 ─ …… ──┤
                                         │
Query ─ IR/Depth查询编码器 ───────────────┘
```

代码主要位于：

- `src/mm_grounding/model.py` 的 `_parallel_backbone_vision_forward`；
- `src/mm_grounding/adapters.py` 的 `ParallelBackboneFusion`；
- `src/mm_grounding/adapters.py` 的 `JointQueryAwareStageFusion`。

## 8. “并行三流”不是三套 Qwen

它不是：

```text
RGB → Qwen A
IR  → Qwen B
Depth → Qwen C
```

仓库没有复制三套各自独立的 Qwen 参数。实际是：

```text
                  ┌─ 处理 RGB
同一套 Qwen 权重 ─┼─ 再处理 IR
                  └─ 再处理 Depth
```

因此：

- 模型主干参数没有变成三倍；
- 视觉 block 的计算会执行三遍；
- 计算时间明显高于 RGB 单流；
- 每种辅助模态有自己的轻量 adaptor。

可以理解成：

> 同一个老师，用同一套知识，分别批改 RGB、IR、Depth 三份试卷。

然后 IR 和 Depth 每经过一个视觉层，都会通过自己的 adaptor 做修正。

## 9. adaptor 到底是什么

adaptor 是加在大模型旁边的小网络。它通常做的是：

```text
原特征
  ↓
降维
  ↓
非线性变换
  ↓
升回原维度
  ↓
乘一个很小的系数
  ↓
加回原特征
```

形式上近似：

```text
新特征 = 原特征 + 很小的修正
```

为什么要乘一个很小的系数？

因为如果新模块一开始是随机的，直接把大量随机信息加到 Qwen 特征中，会立刻破坏 Qwen 原来的 RGB 能力。

所以队友反复使用一个原则：

> 新模块刚初始化时，模型行为应该尽量等同于原来的 RGB 模型。

这叫 RGB-safe initialization，可以翻译为“RGB 安全初始化”。

仓库测试专门验证了：

- 刚初始化时输出是否保持 RGB；
- 新模块之后是否能得到梯度；
- 训练后是否确实能偏离 RGB、学到东西。

## 10. 最终联合融合器在做什么

最终的 `JointQueryAwareStageFusion` 可以理解为一位“会议主持人”。

会议参与者有：

- RGB 特征；
- IR 特征；
- Depth 特征；
- Query 语言特征。

主持人要回答：

> 对当前这条 Query，这三个图像来源谁更可信？

例如 Query 是：

> “最近的行人。”

Depth 可能比较有用。

如果 Query 是：

> “穿红衣服的人。”

RGB 可能最重要。

如果是夜晚：

> “道路右边的人。”

IR 可能帮助发现目标。

联合融合器大致做五件事。

### 10.1 把不同模态转换到同一种表示

RGB、IR、Depth 先经过各自的 projection（投影层），变成相同维度。相当于让三个人使用同一种语言说话。

### 10.2 用 Query 查图像

RGB token 会对 Query 做 cross-attention（交叉注意力）。可以理解为：

> 图像中的每个位置，都去问 Query：“你正在找的是我吗？”

### 10.3 四方注意力

每一个对齐的空间位置上，会同时看：

```text
RGB、IR、Depth、语言
```

这里不是让所有图像位置互相做巨大注意力，而是在对齐位置上比较不同模态，因此计算量相对可控。

### 10.4 判断三个视觉来源是否相互同意

代码显式计算：

- RGB 与 IR 的余弦相似度；
- RGB 与 Depth 的余弦相似度；
- IR 与 Depth 的余弦相似度。

例如：

```text
RGB 说这里有人
IR 也说这里有热目标
Depth 也显示这里有独立物体
```

那么三者较一致，辅助信息更可信。

反过来，如果 IR 图错位：

```text
RGB 的人位于左边
IR 的热目标却位于右边
```

一致性就可能较低。

### 10.5 两层可靠性门控

它有两种 gate（门）：

- token gate：这个具体位置该不该使用辅助信息；
- sample gate：整张样本的辅助模态是否可靠。

最终大致是：

```text
输出 = RGB + token门 × 样本门 × 联合辅助残差
```

如果门接近 0：

```text
输出 ≈ RGB
```

如果门比较大：

```text
输出 = RGB + 有用的IR/Depth信息
```

这就是“辅助模态可靠时使用，不可靠时退回 RGB”的实现。

## 11. 为什么 Query 还要单独编码一次

Query 本来已经给 Qwen 语言模型了，但并行融合器也需要知道 Query 在问什么。

所以代码会：

1. 用冻结的 Qwen embedding 把 Query 变成 token 向量；
2. 使用 `detach` 切断主干梯度；
3. 分别交给 IR 查询编码器和 Depth 查询编码器。

相当于分别告诉两个专家：

```text
IR 专家：这次要找的是“夜间的行人”
Depth 专家：这次要找的是“最近的行人”
```

两个专家可以根据同一句话学习不同的关注方式，同时不修改 Qwen 的词嵌入参数。

## 12. 方案二是怎样一步步训练出来的

这条路线不是一次训练完成，而是六个阶段串起来。

### 12.1 Stage 1A：单独训练 IR 分支

使用 RGBT-GroundBench。仓库转换器读取 FLIR、MFAD、M3FD 等来源的 RGB+红外 grounding 标注。

训练时：

- 有 RGB；
- 有 IR；
- 没有 Depth；
- 只训练 IR adaptor、IR Query 编码器和 IR 相关融合参数；
- Qwen 冻结。

配置为 `configs/stage1a_ir.yaml`。

配置中的 `train_50` 表示 50% 分组子集，不是只有 50 条数据。

### 12.2 Stage 1B：单独训练 Depth 分支

使用 RoboRefIt RGB+Depth 数据。

训练时：

- 有 RGB；
- 有 Depth；
- 没有 IR；
- 只训练 Depth 分支；
- Qwen 冻结。

配置为 `configs/stage1b_depth.yaml`。

### 12.3 Joint calibration：联合校准

然后把两个 checkpoint 顺序加载：

```text
IR checkpoint
    +
Depth checkpoint
    ↓
一个同时具有 IR 和 Depth 能力的模型
```

再用目标域人工复核数据进行联合校准。这一步冻结 IR/Depth adaptor，主要避免在较少的目标域数据上破坏已经学会的模态能力。

配置为 `configs/stage2_joint_calibration.yaml`。

### 12.4 Weak 1024

从弱监督目标域数据中选 1,024 条：

- 类别分层；
- 目标尺寸分层；
- 每个场景最多选一条；
- 尽量避免大量相似帧。

然后用很低的学习率训练 1 轮。

配置为 `configs/stage2_weak1024_raw.yaml`。

### 12.5 Clean after weak

弱监督可能带来噪声，所以模型再回到人工复核的干净数据上训练一轮。

可以理解为：

> 先用大量粗糙练习题扩展知识，再用标准答案纠正。

配置为 `configs/stage2_clean_after_weak1024.yaml`。

### 12.6 Joint fusion v2

最后才训练前面讲的联合可靠性融合器。

配置为 `configs/stage2_joint_fusion_v2.yaml`。

这个阶段：

- 加载前面训练好的 adaptor；
- 冻结 IR/Depth adaptor；
- 开启新的 joint fusion；
- 使用 20% 模态 dropout；
- 训练 2 轮。

最终比赛正确率记录为：

```text
0.6785
```

## 13. 模态 dropout 是什么

训练时故意随机丢掉部分辅助模态。

例如原本输入：

```text
RGB + IR + Depth
```

某次训练可能变成：

```text
RGB + Depth
```

或者：

```text
RGB + IR
```

目的不是制造麻烦，而是防止模型形成坏习惯：

> 只要有 IR 就无脑相信 IR，或者只要有 Depth 就无脑相信 Depth。

通过随机缺失模态，模型会学习：

- IR 没有时也能工作；
- Depth 没有时也能工作；
- 两者都不可靠时尽量依靠 RGB。

## 14. 当前实际上只在最后一层做融合

虽然代码支持多个融合阶段，但所有公开并行配置都是：

```yaml
parallel_fusion_stages: 1
```

代码会把唯一的融合位置放在最后一个 Qwen 视觉块后。因此实际流程更准确地说是：

```text
RGB ───── 完整视觉主干 ─────┐
IR  ───── 完整视觉主干+适配 ─┤
Depth ─── 完整视觉主干+适配 ─┤
                              ↓
                        最后统一融合
```

并不是：

```text
每一层都让 RGB、IR、Depth 大规模交互
```

不过 IR 和 Depth 的 adaptor 仍然每层都有。这一点很重要，因为 README 的简化示意图看不出融合具体发生在哪一层。

## 15. 最终 joint fusion 并不是从旧融合器完整继承的

代码中存在一个 warm start helper，可以把旧的 IR/Depth 独立融合器部分参数复制给新的联合融合器。

但最终配置没有开启：

```text
warm_start_joint_fusion_from_legacy
```

实际情况是：

- IR/Depth adaptor 会从前序 checkpoint 加载；
- Query 编码器会加载；
- 旧独立融合参数也存在于模型里；
- 旧融合器被冻结且不参与最终前向；
- 新联合融合器从零恢复投影的 RGB-safe 状态开始训练。

简单说：

> 两位专家沿用之前学到的知识，但最后那位会议主持人基本是重新训练的。

## 16. 数据预处理做了什么

相关实现位于 `src/mm_grounding/data.py`。

### 16.1 RGB

RGB 正常读成三通道彩色图。

### 16.2 IR

IR 先读成灰度图，然后调整到与 RGB 相同尺寸，再转换成三通道。

为什么要变成三通道？因为 Qwen 的图像处理器原本期望类似 RGB 的三通道输入。

### 16.3 Depth

深度图不能直接当普通照片用。队友把它编码成三个通道：

```text
通道1：经过 log1p 压缩的距离
通道2：这个像素的深度是否有效
通道3：全零
```

只保留：

```text
0 < 距离 <= 20米
```

假设原始深度单位是毫米：

```text
原始值 3000
÷ depth_scale 1000
= 3米
```

使用 `log1p` 是为了压缩远距离数值，否则 1 米和 20 米之间的范围可能过大。

第二通道的有效性掩码也很重要，因为深度图中值为 0 往往表示：

> 这里没有测到深度。

如果不提供有效性掩码，模型可能误以为 0 是“离相机零米”。

## 17. 模型是怎么接管 Qwen 视觉前向的

队友没有修改 Transformers 源码，而是在运行时替换 Qwen 视觉模块的 `forward` 方法。

这叫 monkey patch，可以理解为：

> Qwen 原本有一条默认视觉处理路线，队友在模型运行期间临时把它换成自己的三模态路线。

好处：

- 不需要复制和修改整个 Transformers；
- 项目代码比较集中；
- 还能继续使用 Qwen 原本的生成接口。

代价：

- 代码依赖 Qwen 内部结构；
- 必须能找到 `patch_embed`、`blocks`、`merger` 等内部对象；
- Transformers 或 Qwen 实现一旦改变，可能失效。

因此实验 requirements 固定了：

```text
transformers==4.57.3
```

这个版本约束对复现很重要。

## 18. 训练代码实际怎么跑

执行：

```bash
python train.py --config 某个配置.yaml
```

之后会发生：

```text
读取 YAML 配置
      ↓
加载 Qwen Processor
      ↓
加载 Qwen3-VL-2B
      ↓
构造 TriGround adaptor/fusion
      ↓
按顺序加载前序 checkpoint
      ↓
读取训练和验证 manifest
      ↓
构造 DataLoader
      ↓
冻结不该训练的参数
      ↓
训练 → 验证 → 保存 checkpoint
```

主要入口：

- `train.py`；
- `src/mm_grounding/engine.py`；
- `src/mm_grounding/config.py`。

并行路线通常使用：

```yaml
batch_size: 1
grad_accumulation: 8
```

意思是显存中一次只处理 1 条，但累积 8 次梯度后再更新参数。效果近似 batch size 8，但显存压力小很多。

训练还开启了 gradient checkpointing，意思是：

> 前向时少保存一些中间结果，反向时再重新计算，以计算时间换显存。

## 19. 模型到底在优化什么损失

当前发布配置主要训练 Qwen 生成正确文本。

训练样本被组织成：

```text
用户：
[RGB图片]
Locate the object described by: “车辆旁边的行人”
只返回 bbox JSON。

助手：
{"bbox_2d":[120,210,380,840]}
```

代码把用户提示部分的 label 设成 `-100`，意味着：

> 用户问题不计算损失，只监督助手答案。

模型需要学会生成：

- `{`；
- `"bbox_2d"`；
- `[`；
- 四个坐标；
- `]`；
- `}`。

代码虽然保留了：

- coordinate token mask；
- 辅助 bbox L1 loss；
- GIoU loss；
- 辅助 bbox head；

但发布配置将辅助 bbox head 关闭了。所以当前主要是语言模型 token loss，而不是传统检测器的分类损失加回归损失。

## 20. 评估代码怎么工作

评估入口是 `evaluate.py`。

对于最终并行模型，它会分别测试：

```text
RGB + IR + Depth
RGB + IR
RGB + Depth
RGB only
```

这样可以观察：

- IR 是否提供帮助；
- Depth 是否提供帮助；
- 两者一起是否更好；
- 三模态是否反而破坏 RGB。

RDT 路线的实现要求 IR 和 Depth 同时存在，因此只能直接测试：

```text
RGB + IR + Depth
RGB only
```

每个样本生成文本后，代码解析：

```json
{"bbox_2d":[120,210,380,840]}
```

如果解析失败，离线评估会使用：

```text
[0,0,0,0]
```

这相当于给该样本 IoU 记 0。

最终统计：

- mIoU；
- ACC@0.5；
- ACC@0.7；
- L1 坐标误差；
- 输出解析成功率；
- 生成是否撞到最大长度。

## 21. checkpoint 为什么可以拼起来

Stage 1A 只训练 IR，Stage 1B 只训练 Depth。因此两个 checkpoint 分别包含：

```text
Checkpoint A：
IR adaptor
IR Query encoder
IR fusion
```

```text
Checkpoint B：
Depth adaptor
Depth Query encoder
Depth fusion
```

联合训练时按顺序加载：

```text
先加载 A
再加载 B
```

因为两者参数名字不同，加载后就组成一个同时具有 IR 和 Depth 能力的模型。

Qwen 主干不保存在这些 checkpoint 中，因为它完全冻结，可以从 Hugging Face 单独加载。

相关实现位于 `src/mm_grounding/checkpoint.py`。

## 22. 比赛提交工具做了什么

提交入口是 `tools/predict_competition_submission.py`。

它会：

1. 读取官方 Query JSON；
2. 保留 Query ID 和所有原始字段；
3. 临时放一个假的整图 bbox，让 Dataset 能正常构造；
4. 加载模型；
5. 逐条生成预测；
6. 将进度追加到 JSONL；
7. 中断后可以继续；
8. 只替换最终 JSON 的 `bbox`；
9. 检查 Query 顺序、字段和 bbox；
10. 打成 ZIP。

如果模型输出解析失败，默认使用：

```json
[0.0, 0.0, 1.0, 1.0]
```

也就是整张图。这通常不会得到高 IoU，但至少是合法框，不会因为格式错误直接造成提交失败。

## 23. 队友做了哪些数据质量工作

这部分是仓库的重要成果，不只是模型附属脚本。

### 23.1 场景级划分

视频或连续拍摄数据中，相邻帧会非常像。

如果第 100 帧进训练集，第 101 帧进验证集，验证成绩可能虚高。队友实现了按 scene/group（场景/分组）划分，尽量保证同一场景不会同时出现在训练和验证中。

### 23.2 弱数据分层选择

Weak 1024 不是随便抽 1,024 条，而是考虑：

- 类别；
- 目标尺寸；
- 场景多样性；
- 每场景最多一条。

### 23.3 人工审核页面

仓库有本地审核工具，可以：

- 切换 RGB、IR、Depth；
- 查看 GT 框；
- 查看模型预测；
- 标记描述歧义；
- 标记框错误；
- 标记漏标；
- 标记目标太小；
- 标记模态错位；
- 标记“需要 IR”或“需要 Depth”；
- 修正 Query；
- 决定样本进入训练、测试或暂缓。

这说明队友意识到：

> 多模态任务中，数据错位和 Query 错误可能比模型结构问题更严重。

## 24. 历史实验说明了什么

Git 历史中保留了公开发布前的旧日志。

旧验证集上，原生 RGB Qwen：

```text
mIoU      0.4051
ACC@0.5   0.4631
ACC@0.7   0.3687
```

早期多模态模型：

```text
mIoU      0.3441
ACC@0.5   0.3954
ACC@0.7   0.2523
```

加入多模态以后反而更差。

后来旧 Phase B 延长训练到第 10 轮：

```text
mIoU      0.3725
ACC@0.5   0.4364
ACC@0.7   0.2966
```

仍然低于 RGB。

这说明一个重要事实：

> 多一张 IR、Depth 图，不等于模型自动变强。错误融合会让模型变差。

队友后续的很多设计都在解决这个问题：

- 残差尺度很小；
- 零初始化；
- 保留 RGB 主路径；
- 分别预训练 IR/Depth；
- 冻结已经学好的 adaptor；
- 加可靠性门控；
- 使用模态 dropout；
- 增加人工审核。

## 25. 为什么本地结果和比赛结果方向相反

`combined284` 上：

| 模型 | mIoU | ACC@0.5 | ACC@0.7 |
| --- | ---: | ---: | ---: |
| RGB | 0.5848 | 67.25% | 53.87% |
| RDT | **0.5952** | **69.01%** | 54.93% |
| Parallel | 0.5882 | 67.96% | **55.28%** |

看起来 RDT 更好。

但比赛测试是：

| 模型 | 比赛正确率 |
| --- | ---: |
| RDT | 0.6404 |
| Parallel | **0.6785** |

方向完全反过来。

可能原因包括：

1. `combined284` 的 `new154` 与 RDT 弱监督训练数据有重叠；
2. `combined284` 只有 284 条，规模较小；
3. 正式测试集的数据分布不同；
4. Parallel 可能对真正未见场景泛化更好；
5. 训练代码以 mIoU 选 checkpoint，而比赛看 ACC@0.5；
6. 两条路线对不同目标尺寸、Query 类型或场景条件敏感。

其中第一点是仓库文档确认的事实；其余是需要进一步验证的解释。

## 26. 仓库当前最大的指标问题

比赛要优化：

```text
ACC@0.5
```

但训练代码保存最佳 checkpoint 时使用：

```python
metrics["mean_iou"]
```

也就是 mIoU。这两者不是一回事。

假设模型 A 的两个预测 IoU 是：

```text
0.49, 0.49
```

那么：

```text
mIoU = 0.49
ACC@0.5 = 0%
```

模型 B 的两个预测是：

```text
0.51, 0.20
```

那么：

```text
mIoU = 0.355
ACC@0.5 = 50%
```

如果按 mIoU，模型 A 更好；如果按比赛 ACC@0.5，模型 B 更好。

所以当前训练流程可能保存了“平均框更接近”的模型，却不是“比赛做对题目最多”的模型。这是最值得先与 sql 对齐的问题之一。

## 27. 模态诊断脚本有一个盲区

诊断脚本支持把 IR 或 Depth 的残差尺度调大、调小，例如：

```text
IR × 0
IR × 0.5
IR × 2
```

本意是观察模型到底依赖多少 IR。

但脚本目前修改的是旧模块：

```text
stage_fusions
```

最终 v2 使用的是：

```text
joint_stage_fusions
```

所以对最终模型执行这种 scale sweep，活动融合器实际上没有被改。

仍然有效的诊断包括：

- RGB-only；
- RGB+IR；
- RGB+Depth；
- 完整三模态；
- 给模型换一张错误 IR；
- 给模型换一张错误 Depth。

无效的是当前脚本里针对最终 joint 模型的“残差尺度大小”解释。

## 28. 仓库哪些地方做得好

比较扎实的部分包括：

- 两条路线都完整实现，不只是 README 画图；
- 冻结主干，训练成本比较可控；
- 非常重视 RGB-safe 初始化；
- IR 和 Depth 可以独立训练再组合；
- 有场景级数据划分；
- 有人工审核工具；
- 有弱数据分层抽样；
- 有多种模态消融；
- checkpoint 不重复保存 Qwen；
- 比赛提交支持断点续推；
- 测试覆盖融合恒等性、梯度和三流执行；
- 旧 BF16 GradScaler 崩溃已经在当前代码中修复；
- 文档主动承认 `combined284` 数据重叠，没有掩盖。

## 29. 仓库哪些地方还比较乱

当前公开分支不是完全干净的复现包。

主要问题：

- 最新 README 推荐 Parallel；
- 模型卡、注册表、Release 清单仍推荐 RDT；
- 比赛分数只有 README 文字，没有提交记录；
- 数据不在仓库；
- 权重不在 Git checkout；
- 原始评测 JSON 不在仓库；
- 一些旧脚本引用已经删除的配置；
- 两个渲染脚本硬编码 `D:\AIC`；
- `start_reviewer.cmd` 依赖队友自己的目录；
- 提交脚本使用 `tqdm`，但依赖文件没有声明；
- requirements 提到一个已经删除的 `scripts/setup_gpu.sh`；
- 最终 Parallel 发布模型记录为 `last_phase_a.pt`，而不是训练代码选出的 `best_phase_a.pt`；
- 最佳 checkpoint 依据 mIoU，而不是比赛 ACC@0.5。

所以正确理解是：

> 核心模型和实验思路已经具备，但公开整理与实验追溯还没有完全收尾。

## 30. 应该怎样理解整个仓库

把整个仓库压缩成一个故事，就是：

1. 队友先尝试直接把 IR 和 Depth 融入 Qwen；
2. 发现多模态模型反而伤害 RGB；
3. 开始强调“初始时必须等同 RGB”；
4. 做出 RDT-deep，在每层注入辅助提示；
5. RDT 首次在部分指标上超过 RGB；
6. 但弱监督噪声和数据泄漏让本地结果不够可信；
7. 后来改为分别培养 IR 和 Depth 专家；
8. 再用目标域数据让两个专家合作；
9. 最后加入查询条件和可靠性门控；
10. Parallel 在本地小验证集未必占优，但正式比赛从 0.6404 提高到 0.6785。

最简单的类比是：

```text
RDT：
两个没单独受过训练的助手，从解题第一步开始不断给主模型提示。

Parallel：
先把两个助手分别培养成红外专家和深度专家，
最后再让主持人根据问题判断该听谁。
```

比赛结果目前支持第二种做法。

## 31. 讨论前必须向 sql 确认的事情

这些不是让队友重新解释代码，而是补齐实验事实：

1. `0.6785` 对应的精确 checkpoint 是不是发布的 `triground-parallel-a-v1.pt`？
2. `0.6404` 和 `0.6785` 是否来自完全相同的比赛轮次和测试集？
3. 是否有提交 ID、排行榜截图或结果回执？
4. 为什么 Parallel 发布的是 `last_phase_a.pt`，不是 `best_phase_a.pt`？
5. 是否按 ACC@0.5 重新比较过每个 epoch？
6. Weak 1024 与 `combined284/new154` 有没有重叠？
7. RGB、RGB+IR、RGB+Depth、完整三模态分别是多少？
8. 错配 IR/Depth 后成绩是否明显下降？
9. 最终 joint fusion 的实际提升是多少，还是主要提升已经在独立 adaptor 阶段出现？
10. 比赛预测时 fallback 了多少条无法解析的输出？

这十个答案基本能判断：

> 0.6785 到底是稳定、可复现的模型能力，还是某个 checkpoint、数据划分和提交细节共同造成的结果。
