# GPT Pro审计复核、云端数值取证与下一步判断

2026-09-27。已完整阅读用户提供的467行审计，逐条对照真实代码、既有预测和训练记录，并按用户补充授权只读核查云电脑的10个历史检查点及优化器。原文保存在 [pro-audit-original.txt](pro-audit-original.txt)。本报告不是GPT Pro意见的照单采纳，也没有执行其建议的新训练。

## 结论

**采纳其主要诊断：新增对应监督没有充分约束辅助证据驱动的目标选择，冻结C的全量选择/细化接口也没有被验证可靠。保留C、停止将当前细化链当成改进方案，是合理取舍。**

但下一步不宜立即把所有资源押在“唯一候选纠错器”上。本轮云取证发现一个具体的数值条件：三条200步训练的前后阶段分别保存为BF16和FP32，参数及Adam状态同步变化。它比笼统的“可能全程BF16”更准确，应该先把初始化/恢复的精度策略固定，再验证新的学习目标。

需要纠正或收窄的主要内容：

1. **35条含Depth数值提示的题，C命中27条，不是32条。**32属于全部43条相机近远题。对应的理论剩余空间是8题，而非3题；19条有可靠候选对的题中C命中15条。以上都只是错误计数上限，不是Depth可实现增益。
2. **真实LoRA并非全程BF16，也没有整体停止学习。**前100步A元素端点变化约12%，B约98%，有效BA变化明显；100→200阶段升为FP32。没有记录逐步梯度和写入，不能从端点不变直接断定每一步都被吞掉。
3. **LFPR“无条件细化全指标更差”只在特定对照成立。**其Ref-L4附录部分无门槛细化虽降低ACC@0.5，却提高较高IoU指标；不能把它当作所有细化必坏的定理。RGBX-R1的19.64与31.04数字属实，但不是思维链的严格单因素效应。
4. **“本地两份5690预测不同”不等于已核实平台实际上传了不同文件。**本轮复算1107框相同、4583不同、其他字段一致；只能排除本地包内容相同。官方0.7144和上传动作仍是用户反馈/未独立查证。

## 最重要的新证据：真实训练在恢复边界切换精度

云端环境实际为torch 2.8.0+cu128、PEFT 0.20.0、Transformers 5.14.1。只读取adapter和optimizer，没有构造8B模型，没有调用GPU。

| 历史检查点 | 288个LoRA张量 | Adam一阶/二阶状态 |
|---|---|---|
| M2 checkpoint-928 | FP32 | FP32 |
| B/G*/U* checkpoint-100 | BF16 | BF16 |
| B/G*/U* checkpoint-200 | FP32 | FP32 |
| C phase1 checkpoint-500 | BF16 | BF16 |
| C phase1 checkpoint-1000 | FP32 | FP32 |
| C phase2 checkpoint-500（最终C） | BF16 | BF16 |

各检查点均为rank32、alpha64、普通LoRA，缩放系数2。真实installed `transformers/trainer.py:3426` 恢复时调用 `model.load_adapter(..., is_trainable=True)`；真实 `peft_model.py:1412` 的 `autocast_adapter_dtype` 默认True，`:1581–1584` 执行转换。项目启动器首次载入却显式False。**这解释了为何同一训练在续跑后改变精度；学习率轨迹和消费顺序正确并不足以保证数值条件始终相同。**

为了排除加载舍入，比较M2→100时先将M2转到目标BF16再比较。三臂前100步：A的端点变化比例为12.12%–12.17%，B为98.33%–98.51%；BA相对变化11.43%–14.64%。100→200：A/B均近100%发生端点变化，BA相对变化4.29%–4.53%。这是历史权重差，不是逐步更新率；两段学习率、输入样本不同，不能由这两个比例算出“FP32效率高几倍”。

因此Pro的数值风险有真实依据，但“它就是分数瓶颈”仍需受控实验。三臂共享同一精度切换策略，所以B/G*/U*的原比较仍是该策略下的有效结果，不能借数值问题注销负结果或推定U*其实会胜出。下一次训练应明确保存/恢复前后的可训练参数和状态精度，不能只检查288个张量有梯度。

完整证据见 [numeric-audit.md](numeric-audit.md)、[云端取证JSON](cloud-checkpoint-audit.json)、[配置补读](cloud-adapter-configs.json)。CPU小例只展示舍入机制，和真实云权重统计分开保存。

## 对照官方赛题与文献后的取舍

官方PDF第2–4页要求以Query为语义引导，利用RGB/IR/Depth定位RGB单框，主指标是全Query分母的ACC@0.5。第3页说明官方原始Depth为毫米uint16、IR为8位灰度堆叠、模态已人工对齐；这些不能无条件推广到外部可视化Depth或JPEG。第7–8页允许外部训练数据，但不允许官方测试数据用于训练、人工生成测试框或闭源在线API进行比赛预测。设计里的训练标签/人工关系确认应来自合法训练来源，不能从5690官方集取样造监督。

官方参考的 [RGBDT500/RDTTrack论文](https://proceedings.neurips.cc/paper_files/paper/2025/file/b4962fcd5d4410a9f43ef70f528eedd8-Paper-Datasets_and_Benchmarks_Track.pdf) 也是一个值得警惕的任务差异：它从已给定目标模板/位置做视频跟踪，使用模板与搜索区域，不等于从英文Query在同场景竞争对象中找唯一目标。可借三模态互补和来源数据，不能把跟踪框直接改写成自然Query后就认定具备关系监督。论文第3.1节描述ZED RGB/Depth像素对齐及IR目标区域手工映射，却没有给出本地外部Depth文件数值单位的充分证明；本轮维持单位未核实状态。

论文支持的是可借机制，不是必须采用某一结构。[Rex-Thinker](https://arxiv.org/html/2506.04034) 使候选裁决接受专门监督；[SpatialRGPT](https://arxiv.org/html/2406.01584) 显式构建区域关系；[RGB-Th-Bench](https://arxiv.org/html/2503.19654) 把热图能力拆开测。[RGBX-R1](https://arxiv.org/html/2602.00504) 的完整训练链不能缩写为“加思维链即可”；[LFPR](https://arxiv.org/html/2608.19553) 的接纳策略、指标曲线和开发集边界值得借鉴，但不能在本赛复制阈值承诺收益。[FLIR的发射率说明](https://www.flir.com/discover/professional-tools/how-does-emissivity-affect-thermal-imaging/) 则支持把局部热亮度作为有条件的证据，而不是无条件对象选择规则。

具体方法、表格上下文与查阅限制见 [文献核查报告](literature-audit.md)。没有运行这些论文模型；没有把论文成绩拼成可横比榜单。

## 反思与下一步

过去的问题不只是监督量不足，而是验收对象错了：跨图框相近可以过IoU，JSON合法可以过预检，梯度非零可以过训练检查，三者都没有直接证明“用正确辅助证据返回更好的RGB框”。上一轮接手审计核实了消费顺序、LR和恢复文件要求，却没有取得云参数精度，是一个实际缺口；本轮补查揭示恢复边界的精度变化。

下一步按两个问题推进：先让同一训练的数值条件明确且稳定，再检验与最终输出一致的纠错学习。候选方法优先复用已有资产，先做一个完整方法与C的固定比较；不用大规模对象图、标注平台或消融矩阵把试验推迟。若要宣称辅助模态作用，再做小而匹配的内容对照。详细的动作定义、KEEP与无解样本处理、数据划分、短数值比较、成功/停止条件见 [下一实验方案](next-experiment-proposal.md)。

这一优先级仍可被实验推翻：若稳定精度后的直接定位已明显改善，先利用该收益；若选择器只有RGB能力增益，就如实称候选选择改善；若辅助证据不具判别力，不继续堆同类对应标签；若候选漏检是主要剩余问题，再动候选生成。不能把任何一次小开发集净增包装为已证明泛化。
