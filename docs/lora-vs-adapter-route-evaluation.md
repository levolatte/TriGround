# 两条路线的评估：Adapter 融合（初赛）vs 语言 LoRA（现在）

> 本文回答一个问题：项目在初赛投入的**模态融合架构**，与现在走的**语言侧 LoRA + 三图直输**，
> 各自的价值是什么？结论必须能经受"是否分离了变量"的检验。
> 事实来源：`docs/research/2026-08-28-triground-repository-analysis.md`、
> `2026-09-05-gpt-pro-triground-audit-review.md`、`2026-09-08-contest-and-current-code-review.md`、
> `2026-09-11-pipeline-audit.md`，以及 `code/src/mm_grounding/adapters.py` 源码。

---

## 1. 两条路线到底在做什么

### 路线甲：Adapter 融合（初赛）

**基座**：`Qwen3-VL-2B-Instruct`（冻结）

两条子路线，都在**视觉侧**动刀：

| 子路线 | 机制 | 初赛成绩 |
|---|---|---|
| RDT 弱监督早期融合 | IR/Depth 先形成视觉提示，在**每个视觉块前反复更新并注入** | 0.6404 |
| 并行三流 + 查询条件联合融合 | RGB/IR/Depth **共享同一套冻结视觉块权重**分别前向；IR/Depth **每层接轻量残差 adaptor**；最后在**查询条件下**做联合可靠性融合 | **0.6785** |

**训练链**：五阶段——`stage1a_ir`（RGBT-GroundBench 学红外适配器）→
`stage1b_depth`（RoboRefIt 学深度适配器）→ `stage2_joint_calibration` 等。
发布权重约 45.06M 可训练参数、178 次更新，**依赖两个外部数据集**。

**代码规模**：`adapters.py` **1001 行** + `model.py` **782 行** = 约 1783 行自定义模型代码，10 个融合类。

### 路线乙：语言 LoRA + 三图直输（现在）

**基座**：`Qwen3-VL-8B` → `Qwen3.6-27B`（冻结）

- 三张图（RGB/红外/深度）**作为三个普通图像输入**，靠 prompt 说明顺序与深度含义
- **只训语言侧 LoRA**（q/k/v/o，8B 上是 144 个模块 / 30.67M 参数），视觉塔与 merger **完全冻结**
- **没有任何视觉侧适配器、没有融合模块**
- **不需要外部数据集**，只用目标域 City 数据

**代码规模**：`native_lora_training.py` 268 行 + 数据准备 267 行 ≈ **535 行**，
**零自定义模型代码**（直接用 HF 与 ms-swift）。

**⚠️ 关键**：路线乙**同样用了三模态**（三张图都输入）。所以"模态训练有没有用"与
"要不要显式融合架构"是**两个不同的问题**，不能混为一谈。

## 2. 成绩链与它证明了什么

| 阶段 | 配置 | 官方成绩 |
|---|---|---|
| 初赛 | 2B + Adapter（RDT / Parallel） | 0.6404 / 0.6785 |
| 初赛 | **原生 8B**（用户提供） | **< 0.7** |
| 复赛 | 微调 8B（语言 LoRA @602112） | **0.7144** |
| 复赛 | **零样本 27B @原生** | **0.7685** |

**能得出的结论**：

1. **微调（含三模态训练）确实有效**：8B 从初赛 `<0.7` 提到复赛 `0.7144`，
   即 **≥ +1.44pp**。这与用户判断一致——模态训练不是没用的。
2. **模型规模 + 原生分辨率的杠杆更大**：零样本 27B（**完全没训**）拿到 0.7685，
   比微调 8B 再高 **+5.41pp ≈ +308 题**。

**不能得出的结论（重要）**：

- ❌ **"LoRA 路线优于 Adapter 路线"** —— 两者基座不同（2B vs 8B/27B），
  **规模是未分离的混淆变量**。
- ❌ **"显式融合架构没用"** —— 从未在**同一基座**上比较过"有融合模块"与"无融合模块"。
- ❌ **"模态训练没用"** —— 路线乙本身就吃了三模态输入。

**目前证据支持的、最克制的说法是**：

> 在**没有**显式融合架构、只做语言侧 LoRA 的情况下，三模态输入 + 更大基座 + 原生分辨率
> 可以达到 0.7685。这**不否定**融合架构的价值，但说明**它的边际收益需要重新论证**——
> 尤其是当基座自身已有能力做跨模态推理时。

## 3. 一个值得注意的旁证

`docs/research/2026-08-11-contest-understanding.md` 早就记过一条相反的提醒：

> CVPR 2026 GroundingME 在同一 Accuracy@0.5 口径下，Qwen3-VL-8B Thinking 为 34.3，
> A22B 为 49.8；**不能迷信模型规模**。

而本次实测是"规模大幅有效"。两者不矛盾——**benchmark 分布不同**。
这恰好说明：**本赛题上，规模与原生分辨率的收益被此前的本地开发集系统性低估了**
（见 `docs/qwen36-27b-sprint.md` 的官方锚点一节：本地 +5 题 → 官方 +308 题）。

## 4. 要分离变量，需要哪两个实验

| # | 实验 | 回答的问题 | 成本 |
|---|---|---|---|
| **E1** | **零样本 8B** 在 City412 / 官方上评测 | "微调本身"值多少题（当前最大缺口） | City412 约 7 分钟；官方 1 次提交 |
| **E2** | **2B + 语言 LoRA**（同基座下对照 Adapter） | 同规模下，显式融合架构 vs 纯 LoRA 谁强 | 2B 训练 + 推理，成本低 |

**E1 是当前最该补的**：它把"微调贡献"与"规模贡献"彻底分开，
是技术报告里论证创新点的**决定性证据**。而且它很便宜。

**E2 只有在半决赛还有余量时才值得做**——它的结论对"是否保留融合架构"有指导意义，
但对本次复赛成绩没有帮助。

## 5. 对技术报告的建议

如实按贡献排序，不夸大战绩归因：

1. **基座换代 + 原生分辨率**（本轮验证的最大杠杆：零样本即 0.7685，比历史最好高 5.41pp）
2. **三模态输入的训练**（8B 上至少 +1.44pp；27B 上待本轮训练验证）
3. **工程上的可信度**（两道正确性闸门、提交格式闸门、以及被实测否决的前缀缓存优化——
   这些体现的是"不把未验证的东西交上去"的工程纪律）
4. **融合架构的历史价值**：应诚实写成"在 2B 基座上有效（0.6404→0.6785），
   但在更大基座上其边际收益尚未被分离验证"，**而不是**暗示它是当前成绩的来源。

**特别提醒**：不要写"我们用 LoRA 替代了 Adapter 因而提升"——那是不成立的归因。
